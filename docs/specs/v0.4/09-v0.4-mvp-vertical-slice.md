# v0.4 MVP Vertical Slice

Status: Planned  
Scenario: login requirement -> screen/API -> Playwright test -> test evidence

## 1. Required scope

The MVP must implement through `@archmap/core` plus `@archmap/lifecycle`:

1. Core plugin registry and isolated ArchMap instance API
2. Core generic extension element/relation storage
3. Lifecycle plugin installer
4. Requirement
5. AcceptanceCriterion
6. Decision
7. Risk
8. Test
9. Evidence
10. LifecycleRelation
11. plugin-provided YAML parsing and canonical normalization
12. lifecycle validation
13. generic query and trace API
14. Requirements view
15. Traceability view
16. Quality view
17. JSON model export
18. login vertical-slice sample and automated tests

Release and gates may be represented by relations or deferred until v0.5 after
the foundational model is stable.

## 2. Compatibility contract

- Every v0.3 sample and current automated test passes without source changes.
- Lifecycle collections default to empty when omitted.
- Existing architecture parsing/rendering and public exports do not change.
- New views are projections of the same canonical model, not separate stores.
- Lifecycle sections require `installLifecycle()` (or a configured instance);
  an unconfigured core preserves their source as extensions and reports a clear
  plugin-required diagnostic rather than silently interpreting the vocabulary.

## 3. MVP DSL

```archmap
graph LR
  User[User] --> Login[Login Screen]
  Login --> API[Auth API]
---
requirements:
  REQ-LOGIN:
    title: User can sign in
    type: functional
    status: approved
    priority: must
acceptanceCriteria:
  AC-LOGIN-SUCCESS:
    requirement: REQ-LOGIN
    statement: Successful sign-in displays Home
    given: User is signed out
    when: User submits valid credentials
    then: Home screen is displayed
tests:
  TEST-LOGIN-E2E:
    title: Login end-to-end test
    type: end_to_end
    framework: Playwright
    automated: true
evidence:
  EVD-LOGIN-PASS:
    type: test_result
    status: passed
    producedBy: TEST-LOGIN-E2E
    source: artifacts/login-report.json
relations:
  - { from: REQ-LOGIN, to: Login, type: realized_by }
  - { from: REQ-LOGIN, to: API, type: implemented_by }
  - { from: AC-LOGIN-SUCCESS, to: TEST-LOGIN-E2E, type: verified_by }
  - { from: TEST-LOGIN-E2E, to: EVD-LOGIN-PASS, type: evidenced_by }
```

## 4. Must/Should/Could/Won't

### Must

- Parse and preserve all seven MVP object types.
- Relate Requirement to existing architecture Node.
- Relate AcceptanceCriterion to Test and Test to Evidence.
- Resolve typed relation endpoints and support many-to-many links.
- Render Requirements, Traceability, and Quality views.
- Detect unknown references, duplicate IDs, invalid relation types, missing
  required fields, requirement without acceptance, criterion without test, and
  required test without evidence.
- Preserve v0.3 behavior.

### Should

- Requirement hierarchy, status, priority, owner.
- Risk severity and Evidence status.
- Type/status/owner filters and bounded trace depth.
- Basic coverage counts and JSON export.
- AI authoring guide updates.

### Could

- Goal, Stakeholder, ReleaseGate, GraphPatch, QIF result import, GitHub external
  refs, imports, namespace.

### Won't in v0.4

- Full WorkLens integration, collaborative editing, full ReqIF, SaaS features,
  or every lifecycle object in the long-term model.

## 5. Acceptance criteria

| ID | Criterion |
| --- | --- |
| AC-01 | Existing v0.3 samples/tests pass unchanged. |
| AC-02 | `requirements` parses into the canonical lifecycle model. |
| AC-03 | `trace()` returns Requirement -> Architecture -> Test -> Evidence paths. |
| AC-04 | Requirement without AcceptanceCriterion emits a warning. |
| AC-05 | AcceptanceCriterion without Test emits a warning. |
| AC-06 | Required Test without Evidence emits a warning. |
| AC-07 | Requirements view shows hierarchy, state, priority, and related elements. |
| AC-08 | Quality view shows Requirement/Criterion/Test/Evidence state and links. |
| AC-09 | Requirements and Architecture views derive from one model. |
| AC-10 | Parsed lifecycle model is available as deterministic JSON. |
| AC-11 | Explicit lifecycle IDs survive parse, render, and export. |
| AC-12 | A diagnostic links to the responsible lifecycle object ID. |

## 6. Completion stages

### Stage A — Types and vocabulary

Completion: Core plugin registry, generic extension storage, isolated instance
API, and lifecycle plugin types/installer compile without changing v0.3 output.

Success: AC-01 and stable ID tests pass; installing/uninstalling lifecycle does
not leak global registry state between instances.

### Stage B — Parse and normalize

Completion: YAML sections parse; IDs are stable; relations resolve both
endpoints to lifecycle or architecture elements; extensions are preserved.

Success: AC-02, AC-10, AC-11 pass.

### Stage C — Diagnostics

Completion: structural and three traceability-gap diagnostics emit with target
object IDs and the existing four-level diagnostic model.

Success: AC-04, AC-05, AC-06, AC-12 pass without blocking legacy render.

### Stage D — Query and trace

Completion: type/status filters, reverse lookup, bounded traversal, deterministic
path ordering, and architecture endpoint support.

Success: AC-03 passes for one-to-many and many-to-many fixtures.

### Stage E — Views

Completion: Requirements, Traceability, and Quality base views register through
the existing view API and use the canonical graph only.

Success: AC-07, AC-08, AC-09 pass with readable routing and no component overlap.

### Stage F — Vertical slice and release gate

Completion: the login sample works end-to-end, docs/AI guide are updated, QIF
evidence is recorded, and package/browser compatibility is verified.

Success: all AC-01..12 pass; typecheck, tests, build, browser smoke, and the v0.4
acceptance matrix are green.

## 7. Performance and safety gates

- Benchmark at 100, 1,000, and synthetic 10,000 lifecycle elements.
- Query/trace must not require rendering the complete model.
- Rendered views use filtered subgraphs and avoid mounting unrelated elements.
- External refs and evidence URIs are inert data.
- Labels/diagnostics are escaped; AI proposals cannot create approved evidence.
- Deterministic parse, relation resolution, trace ordering, and JSON output.
